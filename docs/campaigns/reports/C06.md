## Objetivo de la fase

Persistir entidades, relaciones, auditoría y colas sin fuga ni pérdida.

## Entregado en el esqueleto

- src/storage/repository.ts (TenantTable con scoping, unicidad compuesta y CAS)
- src/storage/memory.ts (store completo + audit + webhook receipts)
- src/storage/migrations/0001_schema.sql, 0002_rls.sql, 0003_indexes.sql
- src/storage/pg.ts (PgStore: `set local app.tenant_id` por transacción, sin tenant en los datos)
- scripts/db-verify.ts + `npm run db:verify`: PostgreSQL efímero sin Docker ni root
- scripts/db-persistence.ts + `npm run db:persistence`: escritura en un proceso, reinicio de PostgreSQL y lectura en otro
- src/storage/cases.ts (CaseRepository async: adaptador en memoria y adaptador PostgreSQL)
- src/storage/migrations/0004_case_document.sql: DTO completo del caso en `document`, columnas proyectadas para índices y CAS
- scripts/db-http-durability.ts + `npm run db:http`: el API real contra PostgreSQL, con reinicio del proceso en medio
- src/storage/aggregates.ts (ProposalRepository, ApprovalRepository, IntentRepository, PlanRepository y adaptadores en memoria)
- src/storage/migrations/0005_aggregate_documents.sql: `document` jsonb en propuestas/aprobaciones/intents y tabla `onboarding_plans` con RLS
- scripts/vertical-slices.ts + `npm run slices`: dos vertical slices de punta a punta con dos reinicios del API

## Verificación real ejecutada

- test/tenancy-knowledge.test.ts: scoping, unicidad, CAS en memoria
- `npm run db:verify`: 18/18 garantías en PostgreSQL 18.7 real, conectando como rol no-owner (RLS aplica)
- Lectura aislada A/B, fail-closed sin `app.tenant_id`, insert cruzado 42501, FK compuesta 23503
- Unicidad scoped de `operation_key` y de webhooks, `audit_log` sin UPDATE y sin privilegio DELETE
- PgStore: el tenant no se arrastra entre transacciones de una conexión reutilizada; claim idempotente
- `npm run db:persistence`: 10/10 — caso, contacto, auditoría e idempotencia sobreviven al fin del proceso y a un reinicio del servidor; aislamiento y fail-closed intactos
- `npm run db:http`: 13/13 — con `DATABASE_URL` el API siembra en PostgreSQL, aplica una transición FSM por HTTP y, tras SIGTERM y arranque de otro proceso, devuelve el mismo estado y versión; auditoría durable, CAS con 409 e aislamiento A/B intactos
- `npm run slices`: 20/20 — VS1 (propuesta → preview → aprobación → intent idempotente → despacho sandbox → receipt → delivered → reporte) y VS2 (plan → documento → aceptación → hito done) sobreviven a dos reinicios; A/B aislados y fail-closed sin `app.tenant_id`

## Desviaciones y hallazgos frente a la documentación

- PostgreSQL 18.7 embebido (binarios npm), no la versión de Supabase: las políticas son estándar, falta confirmar en staging.
- El API persiste casos, auditoría, propuestas, aprobaciones, intents y planes cuando hay `DATABASE_URL`; contactos CRUD, outbox y jobs siguen en memoria del proceso.
- El despacho de VS1 es `sandbox_only`: valida la FSM y el receipt, no una entrega a proveedor.
